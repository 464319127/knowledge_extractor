# 0001：采用分阶段、可审核的知识提取管线

日期：2026-07-15
状态：已取代

模型供应商部分已由 [0002：使用 Anthropic Messages 兼容 API](0002-messages-api-adapter.md) 取代。分阶段审核和敏感数据处理决策继续有效。

## 背景

输入日志是模型 API 调用记录。后续请求会重复携带完整历史，一次用户问答还可能跨越多次工具调用。日志同时包含系统提示、工具定义、工具结果、签名、显式推理内容以及本地路径，不能把每一行直接视为一条知识，也不能把原始日志整体交给模型后直接发布其输出。

项目需要从这类日志中生成符合 Open Knowledge Format（OKF）的知识文档，同时满足以下要求：

- 派生结果可以追溯到会话和请求；
- 模型输出必须经过结构校验和人工审核；
- 同一会话中的纠正和失效结论不能并列成为有效建议；
- 原始日志中的敏感或运行时内部内容不能进入知识 bundle；
- 不依赖模型的阶段可以离线测试和重复执行。

## 决策

采用四个显式阶段：

1. `normalize` 使用确定性 Python 代码解析 JSONL，只保留真实用户问题、`end_turn` 完整回答和最小来源标识。
2. `extract` 将规范化问答交给 Gemini，并用 Pydantic 模型校验候选 Concept 和 Claim。
3. 人工在候选 JSON 中把 Concept 的 `review_status` 从 `draft` 改为 `approved`；未批准内容不得发布。
4. `render` 使用确定性代码把已批准候选渲染为 OKF Markdown，并生成目录索引和脱敏的会话证据文档。

`thinking`、`cot_plaintext`、`signature`、系统提示、工具定义和工具调用过程不会写入规范化数据或 OKF bundle。模型不会获得文件写入工具，也不会直接生成最终文件。

第一版最初计划使用 `google-genai` 直接调用 Gemini。模型调用封装在单独适配器中，管线和测试通过协议依赖适配器，避免把供应商 API 扩散到解析、审核和渲染代码。

## 理由

确定性阶段和语义阶段分离后，可以在没有网络和模型凭据时验证绝大多数行为。结构化候选提供了稳定的审核界面，也便于检查来源、冲突和状态。显式 `approved` 门禁可以避免模型把推测或已被纠正的建议直接发布为知识。

直接使用供应商 SDK 比在无工具调用需求的提取阶段引入完整 Agent 编排更简单。保留适配器边界后，未来仍可接入其他模型或离线提取器。

## 影响

- 一份 JSONL 记录不会一对一生成 Concept；Concept 数量由语义主题决定。
- 使用模型前必须配置所选模型适配器的凭据。
- `extract` 的结果只是草稿；自动化 `run` 会停在候选文件，除非输入已经显式批准。
- 原始日志不会被复制进 bundle；bundle 只保存来源哈希、会话 ID、请求 ID 和已清洗的问题。
- 后续增加新的日志格式或模型供应商时，应保持规范化模型和审核门禁兼容。
